Artisan

Architektur

Artisan trennt Spiellogik, Datenverarbeitung, Browser-Anbindung und Rendering. Ziel sind kurze Datenwege, wenige Kopien und eine klare Aufteilung der Aufgaben.

Drei Schichten

Anwendung und API
Der Spielcode definiert Komponenten, Systeme und Szenen. JavaScript bindet die Anwendung in den Browser ein und verarbeitet Eingaben.
Engine-Kern
Der Rust-Kern verwaltet Entities und Komponenten, führt Systeme aus und wird als WebAssembly im Browser ausgeführt.
Renderer
JavaScript übergibt die vorbereiteten Renderdaten an WebGPU. Die GPU zeichnet daraus das Bild.

Die Schichten bleiben über einfache IDs und Speicherinformationen verbunden. Rust kann beispielsweise eine Mesh ID speichern, während JavaScript das zugehörige Mesh verwaltet. So muss der Engine-Kern weder Browser-APIs noch konkrete GPU-Ressourcen kennen.

Bausteine der Game Engine

Artisan stellt die wiederkehrenden Grundlagen einer Spielanwendung bereit. Dazu gehören die World, Systeme, Zeitsteuerung, Eingaben, Transformationen, Assets, Kameras sowie 2D- und 3D-Rendering.

Ein Spiel ergänzt eigene Komponenten, Systeme und Assets. Begriffe wie Siedler, Hunger oder Stämme gehören deshalb zu Vivarium und nicht zur Engine. Dieselbe technische Basis kann so auch für andere Spiele und Simulationen verwendet werden.

Archetype-Speicher

Artisan verwendet den in den Grundlagen beschriebenen Archetype-Speicher als gemeinsame Datenbasis für Systeme, die WebAssembly-Brücke und das Rendering. Dadurch können dieselben zusammenhängenden Komponentenspalten verarbeitet und für den Renderer bereitgestellt werden.

Zero-Copy-Brücke

Zero-Copy bedeutet, dass Daten beim Wechsel zwischen zwei Programmteilen nicht in einen zweiten Speicherbereich kopiert werden. Beide Seiten greifen stattdessen auf dieselben Daten zu. Das spart Kopierzeit, zusätzliche Speicherbelegung und viele kurzlebige Objekte. Besonders bei großen Datenmengen, die in jedem Frame benötigt werden, kann das den Aufwand deutlich reduzieren.

Artisan nutzt dieses Prinzip zwischen Rust und JavaScript. Die Komponentenspalten bleiben im WebAssembly-Speicher. JavaScript legt ein TypedArray über den benötigten Bereich und liest die Werte direkt. Dadurch muss es weder jedes Entity einzeln abfragen noch für jede Komponente ein eigenes JavaScript-Objekt erzeugen.

JavaScript muss direkte Änderungen an den Rust-Kern melden und Speicherverweise bei Bedarf erneuern. Die Evaluation vergleicht diesen Zugriff mit mehreren alternativen Übertragungswegen. Zur Messung

Rendering-Pipeline

Der Rust-Kern wählt sichtbare Entities aus und gruppiert Objekte mit passenden Meshes, Materialien und Shadern zu Batches. JavaScript liest die benötigten Transformationen und Materialdaten aus dem WebAssembly-Speicher und überträgt sie in GPU-Buffer.

WebGPU zeichnet jeden Batch mit Instancing. Dadurch kann ein Draw Call viele Objekte mit demselben Mesh darstellen. Zwischen Hauptspeicher und Grafikkarte bleibt eine Datenübertragung erforderlich. Zero-Copy gilt nur zwischen Rust und JavaScript, nicht zwischen CPU und GPU.

Viele unterschiedliche Assets oder Lücken zwischen sichtbaren Objekten können zusätzliche Batches erzeugen. Die aktuelle Pipeline setzt auf einen einfachen und direkten Datenweg; eine globale Sortierung der sichtbaren Objekte findet nicht statt. Instancing erklärt

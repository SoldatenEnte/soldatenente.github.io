Grundlagen

Drei Bausteine, jeweils von der Grundidee bis zu dem Detail, das später für Artisan entscheidend wird: das Entity-Component-System, WebAssembly und WebGPU.

Entity-Component-System

Ein klassisches Objekt in einem Spiel wird häufig über Vererbung modelliert: ein Gegner erbt von einer Basisklasse, ein fliegender Gegner erbt zusätzlich von einer Flug-Fähigkeit. Solche Hierarchien werden unhandlich, sobald sich Fähigkeiten mischen sollen, die in unterschiedlichen Zweigen der Hierarchie liegen. Ein Entity-Component-System löst das Problem, indem es die Hierarchie ganz weglässt.

Ein Objekt wird stattdessen über die Bausteine beschrieben, die ihm gerade zugeordnet sind. Ein fliegender, angreifbarer Gegner besitzt zum Beispiel die Bausteine Position, Velocity, Health und Flying. Verliert er die Flugfähigkeit, verschwindet nur der Baustein Flying, ohne dass irgendeine Klassenhierarchie angepasst werden müsste.

Entity
Eine bloße Kennung, meist eine Zahl mit Generation. Sie trägt selbst keine Daten.
Component
Ein reiner Datencontainer, zum Beispiel Position { x, y }. Kein Verhalten, nur Werte.
System
Eine Funktion, die über alle Entities mit passenden Komponenten läuft, zum Beispiel: Geschwindigkeit lesen, Position schreiben.
Query
Die Anfrage eines Systems: welche Komponenten müssen vorhanden sein, welche fehlen, und wird gelesen oder geschrieben.

Die Query hat neben der reinen Datenauswahl noch eine zweite Aufgabe. Aus ihr lässt sich ableiten, ob zwei Systeme gefahrlos gleichzeitig laufen können. Lesen beide nur, gibt es keinen Konflikt. Schreibt eines eine Komponente, die das andere gerade liest oder schreibt, ist Gleichzeitigkeit ohne zusätzliche Absicherung nicht sicher. Genau diese Information nutzt später der Scheduler, um Systeme parallel einzuplanen.

Ein kleines Beispiel macht das greifbar und wird im Folgenden für Sparse Set und Archetype weiterverwendet: fünf Entities aus einer einfachen Szene, jedes mit einer anderen Kombination aus vier Komponenten.

Sparse Set und Archetype

Die bisherige Beschreibung legt noch nicht fest, wo die Werte einer Komponente tatsächlich im Speicher liegen. Genau das entscheidet aber darüber, wie schnell ein System durch tausende Entities laufen kann. Zwei Speichermodelle haben sich durchgesetzt.

Ein Sparse Set hält für jeden Komponententyp ein dicht gepacktes Array mit den tatsächlich vorhandenen Werten, dazu eine Indextabelle, die von einem Entity zur Position in diesem Array führt. Einfügen, Entfernen und der direkte Zugriff über ein bekanntes Entity sind dabei sehr günstig. Der Nachteil zeigt sich, sobald eine Query mehrere Komponententypen gleichzeitig braucht: Für jedes Entity muss dann geprüft werden, ob es in allen beteiligten Sets vorkommt, bevor überhaupt gerechnet werden kann.

Nur E1, E2 und E3 aus dem Beispiel oben besitzen Health. Ein Sparse Set für diese Komponente hält deshalb nur drei Werte im dichten Array, dazu eine Indextabelle, die von jedem Entity zur richtigen Position führt:

Ein Archetype-Modell geht umgekehrt vor. Alle Entities mit exakt derselben Kombination von Komponenten landen zusammen in einer Tabelle, ihrem Archetype. Innerhalb dieser Tabelle liegt jeder Komponententyp in einer eigenen, zusammenhängenden Spalte. Eine Query nach Position und Velocity muss dadurch nur die Archetypes finden, die beide Spalten besitzen, und kann sie danach ohne weitere Prüfung Zeile für Zeile durchlaufen. Die fünf Beispiel-Entities von oben verteilen sich dabei auf vier Archetypes, weil vier verschiedene Kombinationen vorkommen:

Der Preis dafür. Der Vorteil des Archetype-Modells ist die dichte, ununterbrochene Iteration. Bezahlt wird er bei strukturellen Änderungen: Verliert E1, der Drache, seine Flugfähigkeit, ändert sich seine Signatur, und es muss komplett von Archetype A nach Archetype B umziehen. Dabei wandert nicht nur die entfernte Komponente Flying, sondern auch Position, Velocity und Health in die neue Tabelle mit.

Beide Modelle schließen sich nicht gegenseitig aus. Bevy speichert standardmäßig in Tabellen und bietet Sparse Sets als Alternative für Komponenten an, die häufig hinzugefügt und entfernt werden. flecs verwendet ebenfalls Archetypes, erlaubt aber zusätzlich Sparse-Komponenten außerhalb der Tabellen. Artisan besitzt im aktuellen Stand nur das Archetype-Modell, keine solche Ausweichmöglichkeit.

Wie stark sich dieser Zielkonflikt tatsächlich auswirkt, misst die Evaluation getrennt für dichte Iteration, strukturelle Änderungen und wahlfreien Zugriff. Zur Messreihe

CPU-Caches

Der Prozessor liest Werte nicht einzeln aus dem Arbeitsspeicher, sondern in Blöcken benachbarter Bytes, den Cache Lines. Werden Werte nacheinander im Speicher gelesen, landen die nächsten benötigten Werte oft schon im Cache, bevor sie überhaupt angefragt wurden. Dieses Prinzip heißt räumliche Lokalität.

Archetype-Spalten sind für genau dieses Muster gebaut: Alle Werte eines Komponententyps liegen direkt hintereinander. Ein Bewegungssystem, das nur Position und Velocity braucht, lädt dadurch keine Namen, Materialien oder Kollisionsformen mit, nur weil diese zufällig zum selben Entity gehören.

Das erklärt, warum ein Vorteil zu erwarten ist. Es belegt ihn aber noch nicht: Wie viel davon in der Praxis ankommt, hängt zusätzlich von der Query-Implementierung, der Zahl der Archetypes, der Breite der Komponenten, der Parallelisierung und der konkreten Hardware ab.

WebAssembly: das Problem und das Format

JavaScript ist dynamisch typisiert, verwaltet Speicher automatisch und lässt kaum Kontrolle darüber, wo genau ein Wert im Speicher landet. Moderne JavaScript-Engines übersetzen häufig durchlaufenen Code zwar zur Laufzeit in schnellen Maschinencode, diese Optimierung beruht aber auf Annahmen über beobachtete Typen. Ändern sich diese Annahmen, kann die Engine den optimierten Pfad wieder verwerfen. Auch wann genau die Garbage Collection läuft, bestimmt nicht die Anwendung.

Für ein Archetype-ECS ist vor allem der fehlende Zugriff auf das Speicherlayout ein Problem: Die ganze Idee der Archetype-Spalten beruht darauf, Komponenten als zusammenhängenden Speicherbereich zu behandeln, den auch eine andere Sprache adressieren kann. Gesucht ist deshalb kein Ersatz für JavaScript als Ganzes, sondern ein Ausführungsformat für genau den rechen- und speicherintensiven Teil, den Engine-Kern.

WebAssembly ist ein sicheres, portables Low-Level-Format. Es definiert ein Binärformat, ein lesbares Textformat und die Semantik einer stackbasierten virtuellen Maschine. Sprachen wie Rust, C oder C++ übersetzen dorthin. Der Browser validiert ein geladenes Modul und führt es anschließend interpretiert oder in echten Maschinencode übersetzt aus. Ein WebAssembly-Modul ist also kein fertiges natives Programm für eine bestimmte CPU, sondern ein Zwischenformat, das der Browser selbst weiterverarbeitet.

Ausgeführt wird das Modul in einer Sandbox. Es hat keinen freien Zugriff auf das Betriebssystem, das DOM oder andere Browserobjekte, sondern nur auf das, was die Umgebung ausdrücklich als Funktion importiert oder exportiert bereitstellt. WebAssembly ersetzt JavaScript damit nicht, es arbeitet mit ihm zusammen.

Linearer Speicher und die Sprachgrenze

Ein WebAssembly-Modul erhält einen linearen Speicherbereich: einen zusammenhängenden, byteadressierten Block, in dem auch die Heap-Allokationen der übersetzten Sprache liegen. Rusts eigene Typen kennt WebAssembly dabei nicht, für die Laufzeit ist alles nur rohe Bytes an einer Adresse.

Genau dieser Speicher lässt sich von JavaScript aus erreichen. Die Laufzeitumgebung macht ihn als ArrayBuffer sichtbar, bei geteiltem Speicher als SharedArrayBuffer. Darauf lässt sich ein typisiertes Array legen, kurz TypedArray, etwa ein Float32Array, das jeweils vier aufeinanderfolgende Bytes als Kommazahl liest. Kennt die Anwendung Adresse, Elementtyp und Länge einer ECS-Spalte, kann sie diese Werte direkt darüber lesen, ohne für jeden einzelnen ein eigenes JavaScript-Objekt zu erzeugen.

Kostenlos ist der Übergang zwischen den beiden Welten trotzdem nicht. Einzelne Zahlen lassen sich verlustfrei als Funktionsparameter übergeben. Strings, verschachtelte Objekte oder anders aufgebaute Daten brauchen dagegen Umwandlungscode oder eigene Speicheroperationen. Viele kleine Aufrufe über die Grenze hinweg können deshalb in Summe teurer sein als ein einziger gebündelter Zugriff auf denselben Speicherbereich. Werkzeuge wie wasm-bindgen erzeugen zwar die nötigen Bindungen für exportierte Rust-Funktionen, entfernen dabei aber nicht automatisch jede Kopie.

Begrenzte Gültigkeit. Wächst der lineare Speicher, kann die Laufzeit den zugrunde liegenden Buffer austauschen. Ein bereits in JavaScript angelegtes TypedArray zeigt dann weiterhin auf den alten, jetzt ungültigen Buffer und muss neu erzeugt werden. Unabhängig davon kann eine interne Allokation beim Wachsen an eine neue Adresse verschoben werden, und ein Entity kann durch einen Archetype-Wechsel eine neue Zeilenposition erhalten. Zeiger und TypedArrays sind deshalb keine dauerhaft stabile Identität, sondern müssen bei Bedarf neu erzeugt werden.

Genau an diesem Punkt setzt Artisans Speicherbrücke an: Komponentendaten bleiben im linearen WebAssembly-Speicher liegen, JavaScript erhält nur Adresse und Layout, keine Kopie. Zur Brücke

Nebenläufigkeit im Browser

JavaScript läuft im Hauptkontext einer Seite über eine einzige Event Loop. Web Workers eröffnen zusätzliche Ausführungskontexte auf Hintergrundthreads, tauschen mit dem Hauptthread aber normalerweise kopierte Nachrichten aus, keine gemeinsamen Daten.

Ein SharedArrayBuffer durchbricht das: Mehrere Worker können denselben Speicherblock gleichzeitig lesen und schreiben. Sicher wird der Zugriff dadurch allein noch nicht, gleichzeitige Schreibzugriffe können weiterhin Data Races erzeugen. Die Anwendung muss Arbeit konfliktfrei aufteilen oder auf atomare Operationen zurückgreifen. Aus Sicherheitsgründen setzt der Browser dafür außerdem einen cross-origin-isolierten Dokumentkontext voraus, erkennbar an den beiden Headern Cross-Origin-Opener-Policy und Cross-Origin-Embedder-Policy.

Im Rust-Ökosystem stellt Rayon datenparallele Iteratoren und einen Thread-Pool bereit. wasm-bindgen-rayon verbindet dieses Modell mit Web Workers und einem geteilten WebAssembly-Speicher. Artisan exportiert die Initialisierung dieses Thread-Pools und nutzt Rayon sowohl für parallele Query-Iteration als auch für die parallele Ausführung verträglicher Systeme.

Die GPU-Rendering-Pipeline

Eine Grafikkarte ist auf die gleichzeitige Verarbeitung vieler gleichartiger Operationen ausgelegt. Beim klassischen Rasterisierungs-Rendering verarbeitet sie zuerst geometrische Eckpunkte und erzeugt daraus Bildfragmente. Ein Vertex Buffer hält die Geometriedaten, etwa die Ecken eines Dreiecks. Ein Vertex Shader transformiert diese Punkte in den für die Darstellung nötigen Koordinatenraum, ein Fragment Shader bestimmt danach für jedes erzeugte Bildfragment unter anderem seine Farbe.

Ein Draw Call weist die Grafikkarte an, eine Geometrie mit einem bestimmten Zustand zu zeichnen. Seine Kosten liegen nicht nur in der eigentlichen Geometrieverarbeitung: Vorher müssen CPU und Treiber den Befehl kodieren, Zustände und Ressourcen referenzieren und die Arbeit übergeben. Viele kleine Draw Calls können deshalb einen CPU-seitigen Engpass erzeugen, selbst wenn die Grafikkarte pro Aufruf kaum etwas zu tun hat.

CPU- und GPU-Speicher sind außerdem getrennte Bereiche. Daten aus dem JavaScript- oder WebAssembly-Speicher lassen sich nicht einfach als Vertex Buffer verwenden. Die Anwendung muss dafür einen eigenen GPUBuffer anlegen und Daten explizit übertragen, zum Beispiel mit GPUQueue.writeBuffer. Dieser Schritt bleibt nötig, selbst wenn JavaScript den ursprünglichen Wert zuvor ganz ohne Kopie aus dem WASM-Speicher gelesen hat.

WebGPU im Vergleich zu WebGL

WebGL bildet die ältere OpenGL-ES-API für den Browser ab und arbeitet als Zustandsmaschine. Ein Aufruf bindet zum Beispiel einen Buffer oder ein Shader-Programm an den aktuell aktiven Kontext, ein späterer Draw Call verwendet dann den in diesem Moment gültigen Zustand. Die Wirkung eines einzelnen Zeichenbefehls hängt damit von der ganzen Kette vorausgegangener Zustandsänderungen ab, nicht nur von seinen eigenen Parametern. Das erschwert Validierung, Fehlersuche und Parallelisierung sowohl im Treiber als auch im Browser selbst.

WebGPU wurde deshalb nicht als nächste WebGL-Version entworfen, sondern als eigenständiges Modell für moderne Grafikkarten. Zustände werden nicht mehr implizit gesetzt und stillschweigend vorausgesetzt, sondern in expliziten Objekten gebündelt und einmal erzeugt.

Zentral dafür ist die GPURenderPipeline: Sie bündelt Shader, Vertex-Layout und feste Pipelinezustände in einem Objekt, das einmal erstellt und danach mit einem einzigen Befehl aktiviert wird. Ein Command Encoder zeichnet GPU-Operationen auf und erzeugt daraus einen Command Buffer, der gesammelt über eine Queue eingereicht wird. Befehle hängen dadurch nicht mehr von einem einzigen globalen Zustand ab, sondern referenzieren ihre Ressourcen innerhalb klar abgegrenzter Passes und Pipelines. Größere, in sich abgeschlossene Arbeitseinheiten geben der Implementierung außerdem mehr Spielraum für Planung und Optimierung, ohne dass WebGPU dafür auf jede Prüfung verzichtet: validiert wird weiterhin, nur ein größerer Teil davon läuft asynchronisiert auf der eigenen Geräte-Timeline statt bei jedem einzelnen Aufruf.

Neben Renderpipelines kennt WebGPU auch Compute Pipelines für allgemeine parallele Berechnungen, unabhängig von der festen Abfolge aus Vertex- und Fragmentverarbeitung. Beide Pipelinearten werden in WGSL beschrieben, der zu WebGPU gehörenden Shading-Sprache. Artisans reguläre Batch-Pipeline nutzt für die hier betrachtete Darstellung vor allem Renderpipelines mit Instancing; aus der vorhandenen Compute-Unterstützung von WebGPU folgt keine konkrete Nutzung in jedem Renderpfad.

Instancing und Batching

Beim Instancing zeichnet ein einziger Draw Call dieselbe Geometrie mehrfach. Die Vertexdaten des Meshes werden dabei nur einmal übertragen, pro Instanz unterscheiden sich lediglich zusätzliche Werte wie Position oder Materialfarbe.

Die Zahl der Draw Calls sinkt dadurch nur, wenn sich mehrere Objekte tatsächlich gemeinsam verarbeiten lassen. Unterschiedliche Meshes, Shader, Texturen oder andere Pipelinezustände erzwingen getrennte Batches. Eine Engine muss deshalb selbst bestimmen, welche Entities zu einem zusammenhängenden instanzierten Aufruf zusammengefasst werden können.

In Artisan läuft diese Auswahl im Rust- und WASM-Kern, JavaScript setzt anschließend nur die daraus abgeleiteten Draw Calls ab. Die Pipeline ist damit CPU-gesteuert und nutzt GPU-Instancing, ist aber nicht GPU-driven im engeren Sinn, bei dem die Grafikkarte selbst über sichtbare Objekte entscheidet. Zur Pipeline
